# 架构与网关专题

## 题 1：整体架构是怎么设计的

标准答案：

> 整体采用前后端分离加 API Gateway 加多业务微服务的模式。前端包括管理后台、求职者门户和数据大屏；后端按职责拆分为用户、职位、简历、推荐、面试、消息、日志等服务；数据层使用 PostgreSQL、Redis 和 Elasticsearch；AI 能力则通过 OCR、Embedding、RAG 和 Coze 工作流接入简历评估主链路。

## 题 2：为什么要有 API Gateway

标准答案：

> 网关主要解决统一入口问题。前端只需要请求一个地址，网关再根据路径把请求分发到不同服务。同时网关还集中处理日志、限流、CORS 和 WebSocket 代理，这样横切逻辑不需要在每个服务里重复实现。

## 题 3：你的 gateway 是怎么实现的

标准答案：

> 我的 gateway 是基于 Gin 实现的轻量网关，内部维护了一个静态的服务注册表，记录各个微服务地址。HTTP 请求通过 `httputil.NewSingleHostReverseProxy` 转发到目标服务；WebSocket 请求因为普通反向代理不好处理，所以我单独做了 TCP 隧道式代理。除此之外还在网关层挂了日志中间件、按 IP 的令牌桶限流，以及一组统计聚合接口。

## 题 4：网关里的限流是怎么做的

标准答案：

> 我实现的是一个单机内存版令牌桶。每个 IP 对应一个 token 计数器，初始化有固定上限，每秒按固定速率补充 token。请求到来时先尝试扣 token，扣不到就返回 429。这个方案简单直接，适合本地开发和毕业设计，但如果上生产并且网关多实例部署，就需要换成 Redis 之类的分布式限流方案。

## 题 5：为什么网关压测会出现很多非 2xx

标准答案：

> 因为网关默认挂了限流中间件，高并发压测时会触发 429，所以不能拿走网关后的结果直接当核心业务吞吐能力。我的性能验收口径是核心读接口直连微服务，这样更能反映服务自身处理能力。

## 题 6：你的网关只是转发吗

标准答案：

> 不完全是。大多数业务接口确实只是做路径转发，但我在网关里还实现了一组统计接口，比如仪表盘、招聘漏斗、渠道统计、部门进度和趋势数据。这些接口直接从数据库聚合数据返回，属于轻量聚合型网关的设计。

## 题 7：静态服务注册有什么优缺点

标准答案：

> 优点是实现简单、调试方便，很适合本地开发和教学项目。缺点是不支持动态注册发现，也没有健康摘除和自动负载均衡能力。如果后续规模变大，我会引入配置中心和服务发现组件来替代静态映射。

## 题 8：WebSocket 为什么单独处理

标准答案：

> 因为 WebSocket 需要 HTTP Upgrade，普通的 HTTP 反向代理处理起来不够直接。我这里采用了劫持客户端连接加 TCP 隧道转发的方式，把客户端和 message-service 建立的 WebSocket 连接透过去，这样聊天和在线状态场景就能统一从网关入口走。

## 题 9：resume-service 是怎么组织的

标准答案：

> `resume-service` 里我把接口按职责分了几组：`/resumes` 负责简历文件生命周期，`/ai` 负责 AI 能力入口，`/evaluations` 负责评估结果管理，`/applications` 负责投递生命周期。这样读代码时入口比较清晰，也符合业务边界。

## 题 10：这个架构目前最大的不足是什么

标准答案：

> 最大的不足是很多服务虽然代码拆开了，但数据库还是共享的，所以严格来说还不是完全自治的微服务。另外服务治理能力还比较轻，像统一鉴权前置、熔断、链路追踪、配置中心这些还没有完全补齐。
