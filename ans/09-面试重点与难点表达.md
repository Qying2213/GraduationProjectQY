# 面试重点与难点表达

这份资料是 `09` 的增强版，目标不是只告诉你“哪些地方能吹”，而是让你真正能讲清楚：

1. 这个项目整体为什么这样设计。
2. 每个关键步骤在业务里起什么作用。
3. 每个关键步骤背后的原理是什么。
4. 面试官深挖时，你怎么从“我做了什么”升级到“我为什么这么做”。

建议和下面几份资料配合使用：

- `01-项目亮点总表.md`：总览
- `02-项目总述与高频开场题.md`：开场表达
- `03-架构与网关专题.md`：架构细节
- `04-AI链路与推荐专题.md`：AI 和推荐细节
- `05-性能并发与测试专题.md`：性能与测试
- `09-面试重点与难点表达.md`：把上面内容串成“有逻辑的面试表达”

## 一、先记住一个总原则

面试里不要把项目讲成“我做了很多页面和接口”，而要讲成：

> 我做的是一个面向招聘业务全流程的 Go 微服务项目，重点不是单点功能，而是把职位、简历、AI 评估、推荐、面试和消息通知串成一个完整闭环，并且补了权限、日志、测试和性能验证，让它更像一个可交付系统。

这句话里其实已经包含了你最该往外讲的五个方向：

1. 业务闭环
2. 架构拆分
3. AI 工程化
4. 推荐可解释性
5. 质量验证

你面试里最重要的能力，不是“背技术名词”，而是能把下面这条逻辑讲顺：

> 为什么做这个系统 -> 业务流程怎么走 -> 为什么拆成这些服务 -> 为什么 AI 链路要拆这么多步 -> 为什么推荐需要解释 -> 为什么我还要补测试和压测

## 二、项目整体应该怎么讲

### 1. 一句话定位

> 这是一个基于 Go 微服务架构实现的智能人才运营平台，覆盖职位发布、简历管理、AI 评估、智能推荐、面试安排、消息通知和数据看板，核心特点是 AI 能力真正接进了招聘主链路，并且做了推荐解释、风控、权限控制、自动化测试和性能压测。

### 2. 30 秒版本

> 我做的是一个面向招聘场景的智能人才运营平台，前端有管理后台、求职者门户和数据大屏，后端采用 Go 微服务加 API Gateway 的架构，拆成用户、职位、简历、推荐、面试、消息、日志和 AI 评估等服务。项目的核心亮点是把 OCR、Embedding、RAG 和 Coze 工作流接到了简历评估主链路里，同时又补了推荐可解释性、风控、自动化测试和性能压测，让它更接近真实系统而不是普通 demo。

### 3. 1 分钟版本

> 这个项目本质上是在做招聘业务全流程数字化。候选人可以注册、维护在线简历、上传附件简历并投递职位；HR 可以创建职位、查看简历和人才、触发 AI 评估、查看推荐结果、安排面试；消息服务负责通知触达，数据大屏负责可视化展示。技术上我采用了 Go 微服务架构和 API Gateway，把用户、职位、简历、推荐、面试、消息、日志和 AI 评估拆开。最有技术含量的部分有两个：一是 AI 工程化链路，把 OCR、文本清洗、Embedding、RAG 和 Coze 工作流串起来做结构化简历评估；二是推荐可解释性，不只是给分数，还返回 `reason` 和 `match_details`。为了证明这个项目不是只能演示，我还补了全链路接口测试、专项验收和性能压测，核心读接口都超过了 1000 QPS。

### 4. 3 分钟版本的推荐结构

建议你按下面顺序讲，不要一上来先背技术栈：

1. 先讲业务目标：解决招聘流程里的简历处理、推荐解释和流程协同问题。
2. 再讲业务闭环：候选人、HR、面试、消息通知如何串起来。
3. 再讲架构：为什么拆成微服务，网关起什么作用。
4. 再讲 AI：为什么不是直接调模型，而要做 OCR、Embedding、RAG 和工作流。
5. 再讲推荐：为什么不只给一个分，而是要解释。
6. 最后讲验证：测试、验收和压测结果。

## 三、项目整体为什么这样设计

这一节是全局设计逻辑，适合回答“为什么做成这样”。

### 1. 为什么选招聘场景

为什么这样设计：

- 招聘场景天然有完整业务链路，适合做系统化项目。
- 它既有传统 CRUD，又有 AI 增强空间。
- 它天然包含角色差异、权限控制、状态流转和消息触达。

作用：

- 让项目不只是“某个功能页面”，而是一个完整业务系统。
- 方便展示后端、AI、测试、性能多个能力点。

原理：

- 招聘系统的数据流和状态流都比较清晰：职位发布、简历投递、评估推荐、面试安排、消息通知。
- 这种场景非常适合做服务拆分和流程串联。

面试怎么讲：

> 我选招聘场景，是因为它业务闭环完整，而且非常适合把传统业务系统和 AI 能力结合起来。它既能体现后端系统设计，也能体现 AI 工程化能力。

### 2. 为什么前后端分离

为什么这样设计：

- 前端有管理后台、门户和数据大屏三种入口，交互模式差异很大。
- 后端需要支持多个客户端复用同一套接口。

作用：

- 前端可以按场景分别迭代。
- 后端接口更稳定、职责更清晰。
- 更接近企业项目开发形态。

原理：

- 前后端通过 REST API 解耦，前端只关心展示和交互，后端负责业务规则和数据处理。

面试怎么讲：

> 前后端分离不是为了时髦，而是因为我的项目同时有后台、门户和数据大屏，如果做成一体化模板，后续扩展和联调都会更乱。分离以后，后端接口可以被多个前端复用。

### 3. 为什么做成微服务，而不是单体

为什么这样设计：

- 用户、职位、简历、推荐、面试、消息、日志、AI 评估这些模块职责边界比较清楚。
- 毕业设计里如果只是单体 CRUD，架构展示力不够。

作用：

- 每个服务职责更单一，代码结构更清晰。
- 方便局部扩展，比如以后只扩 `resume-service` 或 `recommendation-service`。
- 能展示你对服务边界和系统拆分的理解。

原理：

- 微服务的核心不是“拆成很多服务”，而是“按职责边界拆分，降低模块耦合”。
- 同时你当前是阶段性微服务实现，代码层拆开了，但很多服务仍共享一个 PostgreSQL 数据库。

面试怎么讲：

> 我这里的微服务重点是按业务边界拆分，而不是为了追求服务数量。用户、职位、简历、推荐、面试、消息和日志天然就是不同职责。当前实现是代码层微服务加数据层共享库，这样更适合毕业设计阶段，兼顾架构表达和开发效率。

### 4. 为什么要有 API Gateway

为什么这样设计：

- 前端不应该直接记住一堆服务地址。
- CORS、限流、日志、统一入口这些横切逻辑不适合分散在每个服务里。

作用：

- 统一入口
- 路由转发
- 网关层限流
- 统一日志
- 统一 WebSocket 代理

原理：

- 网关接收统一入口请求，根据路径转发到具体服务。
- 它本质上是系统的“入口层”和“横切关注点聚合层”。

面试怎么讲：

> 我加网关不是只为了转发，而是为了统一前端入口，同时把限流、日志、CORS 和 WebSocket 代理这些横切逻辑集中处理，避免每个服务都重复实现。

### 5. 为什么现在是共享库，而不是一库一服务

为什么这样设计：

- 毕业设计时间有限，优先级是先把完整业务闭环跑通。
- 一库一服务会显著提高联调、迁移和数据一致性处理复杂度。

作用：

- 降低开发和联调门槛
- 更快打通多服务协作链路

原理：

- 当前的取舍是“先完成服务级代码拆分，再逐步收敛数据边界”。
- 这是一种工程阶段性方案，不是理想终态。

面试怎么讲：

> 我知道理想状态是一库一服务，但毕业设计阶段我优先保证业务闭环和开发效率，所以采用了代码层微服务、数据层共享库的方案。这让我能把重点放在业务协作、AI 链路和交付质量上。

### 6. 为什么引入 Redis 和 Elasticsearch

为什么这样设计：

- Redis 适合做热点数据缓存、排行榜和高频只读接口加速。
- Elasticsearch 适合做日志检索和审计追踪。

作用：

- Redis 降低数据库压力，提高响应速度。
- ES 提高日志查询和问题追踪能力。

原理：

- Redis 是内存型 KV 存储，适合低延迟、高频读写。
- Elasticsearch 基于倒排索引，适合全文检索和聚合查询。

面试怎么讲：

> Redis 和 ES 在我项目里不是摆设。Redis 主要承担缓存和热点统计，ES 主要承担操作日志检索和审计能力，这样系统既能更快，也更容易排障。

## 四、把项目按“业务步骤”拆开讲

这一节最重要。面试官真正深挖时，经常不是问你某个技术名词，而是问：

> 一个候选人从上传简历到看到评估结果，中间到底发生了什么？

你要能把整个链路按步骤说出来。

### 步骤 1：候选人注册和身份区分

为什么这样设计：

- 招聘系统天然有至少两类核心角色：候选人和 HR。
- 角色不同，访问的数据和接口完全不同。

作用：

- 候选人只看自己的简历、投递和通知
- HR 看职位、人才、简历、评估和日志

原理：

- 用户登录后拿到 JWT
- 后端通过角色字段和中间件做鉴权
- 后端接口做权限兜底，避免只靠前端隐藏按钮

面试怎么讲：

> 我在项目里做了前后端双层权限控制。前端会按角色隐藏入口，但真正关键的是后端接口也做了 JWT 和角色校验，这样候选人即使手动构造请求也拿不到后台数据。

### 步骤 2：职位发布和职位列表

为什么这样设计：

- 职位是整个招聘流程的起点，没有职位就没有投递、评估和推荐。
- 职位列表是高频读接口，天然是性能重点。

作用：

- 提供职位发布、编辑、关闭
- 给候选人展示职位信息
- 给推荐和 AI 评估提供 JD 上下文

原理：

- `job-service` 负责职位 CRUD、筛选、分页和统计
- 列表查询支持条件过滤和排序
- 高频读接口需要索引和缓存优化

面试怎么讲：

> 职位服务不只是 CRUD，它还是推荐和评估的上游数据源。职位的标题、描述、技能要求和级别这些字段都会进入后面的匹配和 AI 评估逻辑，所以它在整条链路里是一个基础服务。

### 步骤 3：候选人维护在线简历或上传附件简历

为什么这样设计：

- 真实招聘里简历来源并不统一，有人在线填写，有人直接上传 PDF。
- 如果只支持其中一种，场景会很不完整。

作用：

- 在线简历方便结构化维护
- 附件简历更贴近真实用户习惯

原理：

- 在线简历适合结构化存储和表单编辑
- 附件简历适合模拟现实世界里 PDF / DOC 的招聘输入

面试怎么讲：

> 我同时支持在线简历和附件简历，是因为两者代表了两类不同输入：在线简历更结构化，附件简历更真实。这样后面的 AI 评估链路才更有价值，不会只处理理想输入。

### 步骤 4：先做 OCR 或文本提取

为什么这样设计：

- 模型不能稳定处理所有原始文件
- PDF、扫描件、图片简历的文本质量不统一

作用：

- 把文件里的文字提取出来，变成后端可处理文本
- 为后续字段提取、Embedding 和 RAG 提供稳定输入

原理：

- OCR 就是把图片或文档里的可视文字转成文本
- 这一步本质上是在做“非结构化文档 -> 可处理文本”的转换

面试怎么讲：

> 我没有直接把原始简历文件丢给模型，而是先做 OCR 或文本提取，因为后面的字段抽取、Embedding 和 RAG 都依赖稳定文本输入。OCR 是整条 AI 链路的第一步。

### 步骤 5：文本清洗和归一化

为什么这样设计：

- OCR 输出往往带噪声
- 原始文本可能有换行、乱码、空白符、页眉页脚等杂质

作用：

- 提高后续 Embedding 和 LLM 输入质量
- 减少无效噪声对识别结果的干扰

原理：

- 文本质量直接决定后续模型输入质量
- 模型是概率系统，前处理越稳定，输出越可控

面试怎么讲：

> OCR 之后我不会立刻把文本交给模型，而是会先做清洗和归一化。因为如果输入里噪声很多，后面的向量化、RAG 和评估结果都会受影响。

### 步骤 6：为什么要做 Embedding

为什么这样设计：

- 简历和 JD 的匹配不能只靠关键词完全相同
- 需要把文本转成语义向量，支持相似性计算

作用：

- 把简历文本和职位文本转成向量表示
- 为 RAG 和语义匹配提供基础能力

原理：

- Embedding 会把文本映射到高维向量空间
- 语义相近的文本在向量空间里距离更近

面试怎么讲：

> Embedding 的作用是把文字变成机器更容易比较的向量表示。这样系统判断“Go 后端”和“Golang 开发”这种语义相近表达时，不必只依赖完全相同的关键词。

### 步骤 7：为什么要加 RAG，而不是只靠模型

为什么这样设计：

- 模型只看当前简历文本时，容易缺上下文
- 直接把所有上下文塞给模型，成本高且噪声大

作用：

- 给模型补充和当前简历最相关的上下文
- 提高评估和推荐的稳定性

原理：

- RAG = Retrieval Augmented Generation，先检索、再生成
- 先通过向量相似度找到最相关上下文，再把这些上下文送进模型

面试怎么讲：

> RAG 的作用不是替代模型，而是先帮模型找到最相关上下文，再让模型在更有针对性的输入上做判断。这样比直接喂整库数据或者只看单份简历更稳。

### 步骤 8：为什么最终还要走 Coze 工作流

为什么这样设计：

- 前面的 OCR、Embedding、RAG 解决的是输入准备和上下文问题
- 但最终仍然需要模型完成评估、总结和结构化输出

作用：

- 生成多维评估结果
- 输出评分、优劣势、建议和结构化字段

原理：

- 工作流本质上是对模型调用过程做编排
- 相比直接裸调模型，更方便做 prompt 管理、输入输出规范化和后续迭代

面试怎么讲：

> 我最终接 Coze 工作流，是因为它适合承接“结构化评估输出”这一步。前面的 OCR、Embedding、RAG 是准备输入，Coze 工作流负责把这些输入转成业务可消费的结构化结果。

### 步骤 9：为什么同时传 `resume_text` 和 `resume_file`

为什么这样设计：

- 只传文本，可能丢失原始文档上下文
- 只传文件，模型解析稳定性不够

作用：

- 文本做稳定主输入
- 文件做补充兜底

原理：

- 这是双输入策略
- 一个偏稳定性，一个偏保真度

面试怎么讲：

> 我采用了双输入策略。`resume_text` 是稳定输入，`resume_file` 是原始上下文兜底。这样做是为了减少“文本提取不完整导致模型全空”的问题。

### 步骤 10：为什么要把评估结果结构化入库

为什么这样设计：

- 如果只把模型结果当一次性文本返回，就无法复用
- 业务页面、统计、推荐、风控都需要可查询数据

作用：

- 支持前端展示
- 支持历史评估记录
- 支持统计和后续分析

原理：

- 把模型输出转成数据库字段，才能从一次性 AI 响应变成系统能力

面试怎么讲：

> 我不是把模型结果直接吐给前端就结束，而是做了结构化入库。因为只有入库以后，评估结果才能参与后续页面展示、历史记录、统计分析和业务决策。

### 步骤 11：为什么还要做过程追踪

为什么这样设计：

- AI 链路天然黑盒
- 如果只存最终结果，排障会非常困难

作用：

- 知道是 OCR 出错、Embedding 失败、RAG 命中差，还是 LLM 输出异常
- 方便页面回放和问题定位

原理：

- 把整条链路拆成多个阶段，每个阶段都记录状态、错误和辅助信息
- 这样黑盒就变成可观察流程

面试怎么讲：

> 过程追踪是我做 AI 工程化时非常看重的一点。因为如果只看最终分数，你根本不知道问题出在哪。我把 OCR、Embedding、RAG 和 LLM 各阶段状态都记录下来，让这条链路可观察、可排障。

### 步骤 12：为什么推荐不能只给一个总分

为什么这样设计：

- HR 不会因为系统给了 82 分就直接相信
- 业务场景里，决策需要理由，而不是只有结果

作用：

- 提高推荐可信度
- 方便 HR 理解匹配原因
- 方便后续调参

原理：

- 先做多维度打分，再把维度结果聚合成总分
- 解释和分数来自同一套规则，而不是后生成一段好看文案

面试怎么讲：

### 步骤 13：为什么还要做风控

为什么这样设计：

- 结构化提取不等于结果可信
- 招聘场景里，简历真实性和合理性本身就是业务问题

作用：

- 检查时间冲突
- 检查学历和年龄合理性
- 检查经历与技能描述是否明显矛盾

原理：

- AI 负责提取和评估
- 风控负责规则校验
- 这是“模型能力 + 规则能力”的组合设计

面试怎么讲：

> 我觉得只做解析和打分还不够，因为招聘里很关心内容是否可信。所以我又加了一层风控，用规则对结构化结果做时间冲突和逻辑一致性校验，让系统更贴近真实业务。

### 步骤 14：为什么要把面试和消息通知接进来

为什么这样设计：

- 如果链路停在推荐或评估，系统还是不完整
- 招聘流程最终一定要落到面试安排和通知触达

作用：

- 把前面所有判断结果转成真实业务动作
- 形成从候选人到 HR 的闭环交互

原理：

- 业务系统真正有价值，不是停在“看结果”，而是能驱动下一步动作

面试怎么讲：

> 我没有把系统停在评估和推荐，而是继续做了面试安排和消息通知。因为业务闭环的关键不只是判断，更是让系统能推动下一步动作。

## 七、面试官最常追问的“为什么”，你该怎么答

### 1. 为什么不直接做单体

> 因为这个项目的业务边界比较明确，用户、职位、简历、推荐、面试、消息和日志天然就是不同模块。做成微服务更适合表达系统设计能力，也有利于后续扩展。当然我也知道当前仍有共享库，所以它是阶段性微服务实现。

### 2. 为什么不能直接把简历文件丢给大模型

> 因为原始文件解析稳定性不足，文本质量也不可控，出了问题很难排查。所以我先做 OCR 和文本清洗，再做 Embedding 和 RAG，把更稳定的输入交给模型，同时保留原始文件做兜底。

### 3. 为什么要同时传 `resume_text` 和 `resume_file`

> `resume_text` 保证稳定输入，`resume_file` 保留原始上下文。一个偏稳定性，一个偏保真度，这样能降低字段缺失或识别不完整的问题。

### 4. 为什么推荐不能只返回一个分

> 因为招聘决策天然需要理由。HR 不会因为系统说 82 分就直接相信，必须知道为什么匹配、哪些维度强、哪些维度弱，所以我做了多维度解释输出。

### 5. 为什么要做风控

> 因为解析和推荐解决的是“能不能看懂简历”和“像不像合适人选”，但招聘里还要关心“内容可不可信”。风控就是用规则补上这一层。

### 6. 为什么网关压测不能代表全系统吞吐

> 因为网关本身带有限流逻辑，高并发下会返回 429，这反映的是网关治理策略，不是业务接口本身处理能力。所以性能验收口径应以核心微服务读接口直连结果为准。

### 7. 为什么不是完全生产级

> 因为当前项目更偏完整工程化毕业设计实现，已经具备微服务拆分、AI 链路、推荐解释、测试和压测能力，但在配置中心、服务发现、分布式限流、链路追踪和彻底数据解耦这些地方还有继续演进空间。

## 九、哪些话不要乱说

### 1. 不要说成“完全生产级微服务”

更准确的说法：

> AI 提升的是简历处理和推荐能力，但项目整体价值还来自业务闭环、权限控制、系统拆分、测试和性能验证。

### 4. 不要说“我只是调了个模型”

更好的说法：

> 我做的重点不只是调用模型，而是把模型接入一个稳定、可观察、可落库、可被业务页面消费的链路里。

## 十、术语速记

### OCR 是什么

- 全称：Optical Character Recognition
- 中文：光学字符识别
- 作用：把图片、扫描件或 PDF 里的可视文字转成文本

### Embedding 是什么

- 把文本映射成向量
- 让系统能基于语义而不只是基于关键词做比较

### RAG 是什么

- Retrieval Augmented Generation
- 先检索相关上下文，再让模型生成结果

### Coze 工作流是什么

- 一种工作流编排方式
- 适合把模型输入输出做成稳定、可管理的流程

### 可解释推荐是什么

- 不只返回总分
- 还返回匹配原因和维度细节
