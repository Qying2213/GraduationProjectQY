# 项目框架与运行逻辑详解

这份文档的目标是：

- 让你能从全局讲清楚这个项目
- 让你知道“一个请求是怎么跑起来的”
- 让你在面试里不只是会背亮点，而是真的能把系统讲明白

如果面试官问你：

- 这个项目整体是怎么设计的
- 各个服务分别干嘛
- 请求是怎么流转的
- AI 链路怎么跑
- 为什么这样拆分

你就主要看这份文档。

---

## 一、项目一句话定义

这是一个面向招聘业务全流程的智能人才运营平台，采用 **Vue 前端 + Go 微服务 + PostgreSQL/Redis/Elasticsearch + AI 评估链路** 的架构，实现了从职位发布、简历管理、AI 评估、推荐匹配到面试通知的完整闭环。

如果要更口语化一点：

> 我这个项目本质上是一个智能招聘系统，前端有后台、求职者门户和数据大屏，后端按业务拆成多个 Go 服务，并把 OCR、Embedding、RAG 和 Coze 接到简历评估主链路里。

---

## 二、项目整体框架

项目整体可以分成 4 层：

1. 前端展示层
2. 网关入口层
3. 业务微服务层
4. 数据与 AI 能力层

### 1. 前端展示层

前端不是单页面，而是三套入口：

- 企业管理后台
- 求职者门户
- 数据大屏

从前端路由可以直接看出来：

- `/portal/...` 是求职者门户
- `/data-screen` 是数据大屏
- `/` 下的大部分业务页面是后台管理系统

你可以这样讲：

> 前端层面我做了三种界面形态。管理后台给 HR 和管理员使用，求职者门户给候选人查看职位和管理投递，数据大屏用来展示招聘统计数据。这样系统在产品形态上就不只是后台 CRUD，而是具备完整产品结构。

---

### 2. 网关入口层

所有前端请求先打到 `gateway :8080`。

网关主要负责：

- 统一 API 入口
- 按路径路由转发
- 限流
- 请求日志
- CORS 跨域处理
- WebSocket 代理
- 统计接口聚合

你可以这样讲：

> 网关的作用是把多服务入口统一起来，前端不需要记住每个服务地址，只要请求一个基地址。除此之外，网关还负责集中处理一些横切能力，比如限流、日志和跨域。

---

### 3. 业务微服务层

后端主要拆成这些服务：

- `user-service`：认证、登录、JWT、RBAC
- `job-service`：职位发布、职位搜索、职位列表
- `resume-service`：简历上传、OCR、AI 评估、风控、投递
- `talent-service`：人才库管理、人才搜索
- `recommendation-service`：推荐统计、人岗匹配、推荐解释、RAG
- `interview-service`：面试安排、面试状态流转、反馈
- `message-service`：消息通知、未读消息、聊天/WebSocket
- `log-service`：操作日志查询和统计
- `evaluator-service`：独立 AI 评估入口和钉钉推送

你可以这样讲：

> 我按业务边界拆分服务，而不是按技术组件拆。像用户、职位、简历、推荐、面试、消息这些本来就代表不同业务对象，拆开之后代码边界更清晰，也方便后续单独演进。

---

### 4. 数据与 AI 能力层

数据和能力层主要有：

- `PostgreSQL`：核心业务数据
- `Redis`：缓存和部分加速能力
- `Elasticsearch`：日志检索和审计
- `Coze`：工作流评估
- `Embedding API`：向量化
- `OCR`：文本提取

这里最重要的是：

**AI 不是独立外挂，而是嵌进业务链路里。**

---

## 三、项目为什么这样设计

面试官很可能会问：为什么要这样拆？

你可以从 3 个角度讲。

### 1. 业务角度

招聘系统天然就是多模块协作：

- 用户和角色
- 职位
- 简历
- 人才
- 推荐
- 面试
- 消息

如果全放在一个巨大模块里，业务边界会很模糊。

### 2. 工程角度

拆分以后：

- 路由更清晰
- 代码更容易维护
- 不同模块可以单独测试
- 局部问题更容易定位

### 3. 毕设表达角度

微服务架构能更好体现：

- 架构设计能力
- 服务拆分能力
- 接口与边界设计能力
- 系统交付复杂度

你可以这样答：

> 我做微服务并不是为了炫技，而是因为招聘场景的模块边界本来就比较清晰。再加上这个项目还需要接 AI、消息通知、日志和统计，如果都塞在一个单体里会很乱。用微服务拆开后，结构更清晰，也更适合展示工程能力。

---

## 四、项目运行逻辑：从“系统怎么启动”讲起

如果从运行角度理解，这个项目大概是这样跑起来的。

### 1. 启动基础依赖

先启动：

- PostgreSQL
- Redis
- Elasticsearch

它们给后端服务提供数据存储、缓存和日志存储能力。

### 2. 启动后端服务

依次启动：

- gateway
- user-service
- job-service
- interview-service
- resume-service
- message-service
- talent-service
- recommendation-service
- log-service
- evaluator-service

### 3. 启动前端

启动 Vue 前端后，浏览器访问：

- `/login`
- `/portal`
- `/data-screen`

### 4. 前端请求统一打到网关

比如前端请求：

```text
GET /api/v1/jobs
```

请求先到 gateway，再由 gateway 转发到 `job-service`。

---

## 五、一个请求通常怎么跑

你在面试里最常讲的，不是“有哪些服务”，而是“一个请求怎么从前端走到数据库”。

下面我给你 4 条最典型的链路。

---

## 六、链路 1：登录与鉴权

### 流程

1. 前端登录页输入用户名和密码
2. 请求发到 gateway
3. gateway 把 `/login` 转发到 `user-service`
4. `user-service` 校验用户信息
5. 生成 JWT token
6. 前端保存 token 到 store / localStorage
7. 后续请求在 Header 里带 `Authorization: Bearer <token>`

### 这条链路体现了什么

- 统一认证入口
- JWT 鉴权
- 角色权限控制

### 面试回答模板

> 登录链路是这样的：前端把账号密码发给 gateway，gateway 转发到 `user-service`，认证通过后由后端签发 JWT。前端保存 token，后续请求统一带 Bearer Token。这样用户身份和角色信息就能在各个服务的中间件里被识别和使用。

---

## 七、链路 2：职位浏览与搜索

### 流程

1. 前端页面请求 `/api/v1/jobs`
2. gateway 转发到 `job-service`
3. `job-service` 根据分页、筛选、排序参数构造查询
4. 从 `jobs` 表查询职位列表
5. 对每个职位补充申请人数
6. 返回给前端展示

### 这里的细节

这个接口不是最轻的接口，因为它不只是查职位，还会：

- 处理 `page`、`page_size`
- 处理 `status`、`location`、`education`、`keyword`
- 做排序
- 循环查每个职位的申请人数

### 面试回答模板

> 职位列表链路里，前端请求先经过网关，再进入 `job-service`。服务端会根据分页、搜索、地点、学历和经验等参数构造 SQL 查询，取到职位列表后再补充申请人数，最后返回前端。这类接口比简单统计接口更重，因为它同时包含筛选、分页和额外字段补充。

---

## 八、链路 3：候选人投递职位

这是最能体现“完整业务闭环”的链路之一。

### 流程

1. 候选人在门户浏览职位详情
2. 点击投递，前端请求 `/api/v1/applications`
3. gateway 转发到 `resume-service`
4. `resume-service` 通过 JWT 拿到当前登录用户
5. 根据 `user_id` 找到对应 `talent_id`
6. 写入 `applications` 表
7. 读取 `jobs`、`talents` 表补充业务信息
8. 写入 `messages` 表，生成 HR 通知
9. 候选人在“我的投递”能看到记录
10. HR 侧可以在后台看到简历和投递状态

### 这条链路为什么重要

因为它说明：

- 项目不是静态展示
- 数据会在多个业务对象之间流转
- 状态流转是连贯的

### 面试回答模板

> 投递链路里，候选人不是直接把表单写到一个孤立表里，而是要通过 JWT 拿当前用户身份，再映射到人才档案，写入投递记录，最后还要联动消息通知。这条链路体现了用户、人才、职位、投递和消息几个模块之间的真实协作。

---

## 九、链路 4：AI 简历评估主链路

这是你项目最核心的技术链路之一。

### 流程总览

```text
简历文件
 -> 上传到 resume-service
 -> OCR / 文本提取
 -> 文本清洗
 -> Embedding 向量化
 -> RAG 检索增强
 -> Coze 工作流评估
 -> 结构化结果入库
 -> 同步人才档案 / 展示评估结果
```

### 更细一点的过程

1. 用户上传 PDF/DOC/DOCX 简历
2. `resume-service` 保存文件信息和简历记录
3. 调用 OCR 或文本提取获取简历正文
4. 如果提取到有效文本，调用 Embedding API 生成向量
5. 用向量到推荐服务里检索相似上下文，构造 RAG 输入
6. 把 `resume_text`、`resume_file`、`jd_text`、`name` 一起传给 Coze
7. Coze 返回结构化评估结果，包括分数、建议、技能、总结等
8. 结果落入 `evaluation_results`
9. 过程追踪日志写入 `ai_process_logs`
10. 如有需要，同步更新人才库记录

### 你必须讲明白的 3 个设计点

#### 1. 为什么要 OCR

因为简历是非结构化文件，不先提成文本，后续评估就不稳定。

#### 2. 为什么要 `resume_text + resume_file` 双输入

因为只传文件不稳定，只传文本又可能丢掉原始上下文，所以两者一起传更稳。

#### 3. 为什么要做过程追踪

因为 AI 链路是多阶段的，不记录中间过程就很难排错。

### 面试回答模板

> AI 简历评估链路是我项目里最重要的一部分。简历文件上传后，会先经过 OCR 或文本提取，再进行文本清洗；如果文本可用，就做 Embedding 向量化和 RAG 检索增强；最后把 `resume_text`、`resume_file` 和 `jd_text` 一起送到 Coze 工作流做结构化评估。评估结果会落库，整个过程的 OCR、Embedding、RAG、LLM 状态也会记录到过程日志里，用于页面展示和问题排查。

---

## 十、链路 5：推荐与解释

### 流程

1. HR 进入推荐页面
2. 前端请求 `/api/v1/recommendations/...`
3. gateway 转发到 `recommendation-service`
4. 服务端构造职位画像或人才画像
5. 按维度计算匹配分
6. 生成 `reason` 和 `match_details`
7. 返回排序后的推荐结果

### 推荐不是怎么“算”，而是怎么“解释”

核心思想：

- 技能匹配
- 经验匹配
- 地点匹配
- 学历匹配
- 薪资匹配

这些维度先各自算，再形成总分。

### 面试回答模板

> 推荐模块里我没有只返回一个总分，而是把技能、经验、地点、学历和薪资等维度分别计算，再聚合成总分。同时输出 `reason` 和 `match_details`，让 HR 知道结果背后的依据，而不是一个无法解释的黑盒排序。

---

## 十一、链路 6：面试安排与消息通知

### 流程

1. HR 在后台安排面试
2. 请求走 gateway 转到 `interview-service`
3. 面试数据写入 `interviews` 表
4. 结合候选人和职位信息生成消息
5. 写入 `messages` 表
6. 候选人在消息中心或聊天界面看到通知

### 这条链路体现的点

- 后台操作不只是改状态
- 会联动下游消息能力
- 体现了“业务闭环”

---

## 十二、项目里最容易讲混的几个概念

### 1. `user_id` 和 `talent_id`

- `user_id` 是登录账号
- `talent_id` 是人才档案

它们不是同一个东西。

### 2. `Resume` 和 `Application`

- `Resume`：简历文件/简历记录
- `Application`：候选人对某个职位的一次投递行为

### 3. `status` 和 `stage`

- `stage`：流程走到哪一步
- `status`：当前处理结果是什么

### 4. `resume-service` 和 `evaluator-service`

- `resume-service` 是业务主链路中的简历与 AI 评估服务
- `evaluator-service` 更像独立 AI 评估入口和钉钉推送能力补充

---

## 十三、这个项目现在是“怎么跑”的，不是理想化架构

这点很重要，面试里你不要讲成一个过度理想化的系统。

你应该诚实说明：

- 当前很多服务共享一个 PostgreSQL 数据库
- gateway 不是纯转发，还自己做了统计查询
- 限流是单机内存版，不是分布式方案
- AI 链路已经工程化，但还不是工业级可观测平台

这样反而会让你显得更真实、更像真正做过项目的人。

面试标准说法：

> 这个项目是一个偏工程可交付的阶段性实现。架构上已经按服务拆开了，但数据层还是共享库，网关也做了部分聚合统计，所以我不会把它包装成完全成熟的生产级架构。我更强调的是：在毕业设计范围内，它已经具备完整闭环、AI 工程化接入、测试验证和性能指标支撑。

---

## 十四、如果面试官让你“从头到尾讲一遍项目”

你可以用下面这套结构：

### 版本模板

> 这个项目是一个面向招聘业务全流程的智能人才运营平台。整体上分成前端展示层、gateway 入口层、业务微服务层和数据能力层。前端有管理后台、求职者门户和数据大屏；后端用 Go 按用户、职位、简历、推荐、面试、消息和日志等模块拆成多个服务；所有前端请求先经过 gateway，再按路径转发到对应服务。  
>  
> 业务上最核心的链路有两条。第一条是职位和投递链路，候选人注册登录后上传简历、浏览职位并完成投递，HR 在后台查看简历和人才、安排面试，系统再通过消息模块通知候选人。第二条是 AI 评估链路，简历文件上传后先做 OCR 和文本提取，再做 Embedding、RAG 和 Coze 工作流评估，最后把结果结构化落库，并记录过程追踪日志。  
>  
> 我觉得这个项目的亮点主要有四个：一是完整业务闭环，不是单模块 demo；二是 AI 能力真正嵌入主业务流程；三是推荐结果具备可解释性，还补了风控；四是除了功能以外，还做了自动化测试和性能压测，核心读接口 QPS 超过 1000。
