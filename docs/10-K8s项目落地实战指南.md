# Kubernetes 项目落地实战指南

这份文档不是泛泛讲 Kubernetes 概念，而是按你当前这个仓库的真实结构，带你一步一步把项目从 `docker-compose.yml` 迁到 K8s。

目标不是一次性把所有 YAML 堆出来，而是先做出一个最小可运行链路，再逐步扩成完整微服务集群。

## 一、文档目标

跟着这份文档走，你应该能完成 4 件事：

1. 看懂这个项目从 Compose 到 K8s 的资源映射关系。
2. 先把基础设施跑起来：`PostgreSQL`、`Redis`、`Elasticsearch`。
3. 先打通一条最小业务链路：`frontend -> gateway -> user-service -> postgres`。
4. 再把其余微服务按同样模式逐个接入，最终形成完整 K8s 版本。

## 二、先认清你这个项目现在的真实形态

### 1. 当前 Compose 结构

你的 `docker-compose.yml` 现在是这样的思路：

- `postgres`
- `redis`
- `elasticsearch`
- `backend`：一个容器里同时启动多个 Go 服务
- `frontend`

也就是说，Compose 目前偏“打包式部署”，后端虽然代码上是微服务，但容器层面还是“一个 backend 跑很多服务”。

### 2. 当前仓库里已经有的 K8s 基础文件

你已经有这些文件了：

- `k8s/base/namespace.yaml`
- `k8s/base/configmap.yaml`
- `k8s/infra/postgres.yaml`
- `k8s/infra/postgres-init-configmap.yaml`

这说明你已经开始从“Compose 思维”往“K8s 思维”迁了。

### 3. 为什么 K8s 这里不建议继续用一个 backend 容器

因为你已经满足了拆分的两个关键前提：

1. 每个服务都有独立 Dockerfile，比如：
   - `backend/gateway/Dockerfile`
   - `backend/user-service/Dockerfile`
   - `backend/job-service/Dockerfile`
   - `backend/message-service/Dockerfile`
2. 网关已经支持通过环境变量做服务发现：
   - `USER_SERVICE_URL`
   - `JOB_SERVICE_URL`
   - `MESSAGE_SERVICE_URL`
   - 等等

并且你现在的 `k8s/base/configmap.yaml` 已经把这些地址写成了 K8s Service DNS：

```yaml
USER_SERVICE_URL: http://user-service:8081
JOB_SERVICE_URL: http://job-service:8082
MESSAGE_SERVICE_URL: http://message-service:8085
```

这意味着：

- 在 Compose 里，网关默认可以走 `localhost:8081`
- 在 K8s 里，网关应该走 `http://user-service:8081`

所以这套 K8s 方案应该明确采用：

**每个微服务一个 Deployment + 一个 Service**

而不是继续把所有服务塞进一个 `backend` 容器。

## 三、把 Compose 概念翻译成 K8s 概念

先把这个表背下来。

| Compose 概念 | K8s 对应物 | 在你项目里的落地方式 |
| --- | --- | --- |
| service | Deployment + Service | 每个 Go 服务一个 Deployment + 一个 ClusterIP Service |
| environment | ConfigMap / Secret | 普通配置进 ConfigMap，敏感配置进 Secret |
| depends_on | 探针 + 重试机制 | 用 readiness/liveness 代替 |
| ports | Service 端口 | 集群内部 `ClusterIP`，本地测试用 `port-forward` |
| volume | PVC / volumeMount | PostgreSQL、Elasticsearch 用持久卷 |
| network | Namespace + Service DNS | 同命名空间直接用服务名互访 |

## 四、推荐的落地顺序

不要一上来就写十几个 YAML。最稳的顺序是：

### Phase 1：基础设施

先搞定：

- `Namespace`
- `ConfigMap`
- `Secret`
- `PostgreSQL`
- `Redis`
- `Elasticsearch`

### Phase 2：最小可运行链路

先只部署：

- `user-service`
- `gateway`
- `frontend`

为什么先选这 3 个？

- `user-service` 相对基础，依赖简单
- `gateway` 是入口，能验证服务发现是否打通
- `frontend` 已经通过 `nginx.conf` 代理 `/api` 到 `gateway:8080`

只要这一条链路打通，你就证明：

- 集群 DNS 没问题
- ConfigMap/Secret 没问题
- 数据库连通没问题
- 前后端在 K8s 里能跑起来

### Phase 3：逐步接入其余核心服务

按这个顺序扩：

1. `job-service`
2. `talent-service`
3. `interview-service`
4. `resume-service`
5. `message-service`
6. `recommendation-service`
7. `log-service`

### Phase 4：最后再接 `evaluator-service`

它放最后是因为它最特殊：

- Dockerfile 构建方式和其他服务不一样
- 运行时涉及 Python 依赖
- 还依赖 Coze/AI 相关配置
- 当前没有统一 `/health` 探针接口

所以它适合在核心平台跑稳之后再接。

## 九、第四步：补 Redis 和 Elasticsearch

这两个资源现在还没写，但 Compose 里已经有，所以 K8s 版也要补。

### 1. 新建 `k8s/infra/redis.yaml`

推荐先用最简单的本地学习版：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis
  namespace: talent
spec:
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:7-alpine
          imagePullPolicy: IfNotPresent
          args: ["redis-server", "--appendonly", "yes"]
          ports:
            - containerPort: 6379
          readinessProbe:
            tcpSocket:
              port: 6379
            initialDelaySeconds: 5
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 6379
            initialDelaySeconds: 15
            periodSeconds: 10
---
apiVersion: v1
kind: Service
metadata:
  name: redis
  namespace: talent
spec:
  selector:
    app: redis
  ports:
    - port: 6379
      targetPort: 6379
```

### 2. 新建 `k8s/infra/elasticsearch.yaml`

本地学习环境先用单节点版：

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: elasticsearch-data
  namespace: talent
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 4Gi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: elasticsearch
  namespace: talent
spec:
  replicas: 1
  selector:
    matchLabels:
      app: elasticsearch
  template:
    metadata:
      labels:
        app: elasticsearch
    spec:
      containers:
        - name: elasticsearch
          image: docker.elastic.co/elasticsearch/elasticsearch:8.11.0
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 9200
          env:
            - name: discovery.type
              value: single-node
            - name: xpack.security.enabled
              value: "false"
            - name: ES_JAVA_OPTS
              value: "-Xms512m -Xmx512m"
          volumeMounts:
            - name: es-data
              mountPath: /usr/share/elasticsearch/data
          readinessProbe:
            httpGet:
              path: /_cluster/health
              port: 9200
            initialDelaySeconds: 30
            periodSeconds: 10
          livenessProbe:
            tcpSocket:
              port: 9200
            initialDelaySeconds: 60
            periodSeconds: 20
      volumes:
        - name: es-data
          persistentVolumeClaim:
            claimName: elasticsearch-data
---
apiVersion: v1
kind: Service
metadata:
  name: elasticsearch
  namespace: talent
spec:
  selector:
    app: elasticsearch
  ports:
    - port: 9200
      targetPort: 9200
```

## 十、第五步：先做最小可运行链路

这一阶段我们只做：

- `user-service`
- `gateway`
- `frontend`

### 为什么不是一上来全量部署

因为 K8s 新手最容易在下面这些点一起踩坑：

- 镜像没构建对
- Service 名字不对
- ConfigMap 环境变量没注入
- 数据库 DNS 不通
- 探针路径写错
- 前端代理地址不对

所以先只打通一条链路，问题会少很多。

## 十六、第十一步：最后再接 evaluator-service

这一步建议单独对待。

### 原因

它和其他服务不太一样：

- Dockerfile 构建上下文不同
- 同时依赖 Go 和 Python 运行环境
- AI 配置更多
- 当前没有现成 `/health`

### 构建命令

```bash
docker build -f backend/evaluator-service/Dockerfile -t talent/evaluator-service:local backend/evaluator-service
```

### 你的两个选择

#### 选择 A：先用 TCP 探针

优点：最快能跑起来。  
缺点：不够细致，不能判断业务是否真正健康。

#### 选择 B：先给 evaluator-service 补一个 `/health`

优点：更标准，也更适合面试讲。  
缺点：需要先改代码。

如果你是为了“练 K8s + 提升工程能力”，我建议你选 B。

## 十七、第十二步：本地先用 port-forward，不要急着上 Ingress

很多人学 K8s 的时候太早碰 Ingress，结果把问题复杂化。

你现在应该先用：

```bash
kubectl port-forward -n talent svc/frontend 3000:80
kubectl port-forward -n talent svc/gateway 8080:8080
```

等所有 Pod 和 Service 都稳定后，再补：

- `Ingress`
- 自定义域名
- HTTPS

- `k8s/base`

- `k8s/apps`

## 二十、你现在最容易踩的坑

### 1. Secret 没建，PostgreSQL 起不来

这是你当前仓库里已经存在的坑。

### 2. 网关地址没改成 Service DNS

如果你在 K8s 里还让 gateway 去找 `localhost:8081`，那一定不对。

在 K8s 里它应该去找：

```text
http://user-service:8081
```

### 3. 直接照搬 Compose 的 backend 单容器思路

这会和你当前 `k8s/base/configmap.yaml` 里的服务发现策略冲突。

### 4. 过早引入 Ingress

先用 `port-forward` 把服务跑通，再上 Ingress。

### 5. 探针写太激进

像 Elasticsearch 启动慢，`initialDelaySeconds` 太短会反复重启。

## 二十一、我建议你的实际练习路径

如果你现在要真正动手，我建议按下面 7 步练：

1. `kubectl apply` 现有 `namespace.yaml` 和 `configmap.yaml`
2. 自己写 `secret.local.yaml`
3. 跑起 `postgres`
4. 自己写 `redis.yaml`
5. 自己写 `user-service.yaml`
6. 自己写 `gateway.yaml`
7. 自己写 `frontend.yaml`

只要第 7 步完成，你就已经不是“只会看 K8s 教程”的状态了，而是开始真正把项目迁到集群里了。

## 二十二、下一步应该做什么

如果你准备继续往下做，最合理的顺序是：

1. 先按本文把 `secret.local.yaml`、`redis.yaml`、`user-service.yaml` 写出来
2. 再写 `gateway.yaml`
3. 最后写 `frontend.yaml`

这样你每写完一个文件，都能立刻 `kubectl apply` 验证，不会积累太多未知错误。
