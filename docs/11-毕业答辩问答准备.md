# 毕业答辩问答准备

> 适用项目：智能人才运营平台  
> 答辩重点：招聘业务流程 + Go 微服务 + Vue 前端 + OCR/Embedding/RAG/Coze AI 评估链路

## 一、项目整体介绍

### 1. 你的项目是做什么的？

可以这样回答：

我的项目是一个智能人才运营平台，主要面向企业招聘场景。系统包含企业管理后台、求职者门户和数据大屏，支持人才管理、职位管理、简历上传、简历 AI 评估、人岗匹配推荐、面试安排、消息通知、操作日志等功能。

项目的核心不是单纯做 CRUD，而是把 OCR、Embedding、RAG 和大模型工作流接入招聘流程，帮助 HR 更快地解析简历、判断候选人与岗位的匹配度，并生成可解释的评估结果。

### 2. 你这个项目解决了什么实际问题？

可以这样回答：

传统招聘中，HR 需要人工阅读大量简历，效率低，而且不同 HR 的判断标准可能不一致。我的系统通过自动解析简历、语义匹配职位要求、生成 AI 评估报告，帮助 HR 快速筛选候选人，提高简历处理效率和匹配判断的一致性。

### 3. 你的毕业设计核心功能是什么？

可以这样回答：

核心功能是简历 AI 评估和智能推荐。具体来说，`resume-service` 负责简历上传、OCR 文本提取、调用 Coze 进行评估，并保存评估结果；`recommendation-service` 负责 Embedding 向量化、RAG 检索和人岗推荐。这两部分共同构成项目的智能招聘能力。

### 4. 你项目里哪些功能是基础业务，哪些是创新点？

可以这样回答：

基础业务包括用户登录、人才管理、职位管理、简历管理、面试管理、消息通知和操作日志。创新点主要是 AI 简历评估、人岗语义匹配、RAG 检索增强、评估过程可解释化，以及把这些能力嵌入完整招聘流程中。

### 5. 你的一句话项目总结是什么？

可以这样回答：

我的项目是一个基于 Go 微服务和 Vue3 的智能人才运营平台，核心是将 OCR、Embedding、RAG 和 Coze 大模型工作流结合到招聘流程中，实现简历解析、人岗匹配、智能推荐和可解释 AI 评估。

## 二、系统架构相关

### 6. 你的系统整体架构是什么？

可以这样回答：

系统采用前后端分离和微服务架构。前端使用 Vue3、Vite、Pinia、Vue Router 和 Element Plus；后端使用 Go 语言开发多个微服务，包括用户服务、职位服务、人才服务、简历服务、推荐服务、消息服务、面试服务、日志服务和 API Gateway。

API Gateway 统一对外暴露接口，前端只需要访问网关，由网关转发到对应业务服务。

### 7. 为什么要使用微服务架构？

可以这样回答：

因为招聘系统本身包含多个业务边界，例如用户、职位、人才、简历、推荐、消息、面试和日志。用微服务拆分后，每个服务职责更清晰，方便独立开发、维护和扩展。比如 AI 推荐能力主要集中在推荐服务和简历服务中，不会和用户登录、消息通知等逻辑混在一起。

### 8. 微服务架构有什么缺点？你怎么处理？

可以这样回答：

微服务会带来部署复杂度、服务间通信、端口管理和调试成本增加的问题。我的项目通过 API Gateway 统一入口，通过启动脚本统一启动和停止服务，并使用健康检查和日志目录来排查服务状态。对于服务间内部调用，比如 `resume-service` 调用 `recommendation-service`，使用内部接口和 `X-Internal-Token` 区分普通用户请求和服务间请求。

### 9. API Gateway 在项目中做什么？

可以这样回答：

API Gateway 是系统的统一入口，运行在 `8080` 端口。它负责把 `/api/v1/users`、`/jobs`、`/resumes`、`/recommendations`、`/messages` 等请求转发给不同微服务，同时处理跨域、限流、Swagger 文档和 WebSocket 转发。这样前端不需要知道每个微服务的真实端口。

### 10. 你的服务之间是怎么通信的？

可以这样回答：

主要使用 HTTP REST 方式通信。前端通过 Gateway 调用后端服务；后端服务之间也会通过 HTTP 调用内部接口。例如 AI 评估时，`resume-service` 会调用 `recommendation-service` 的 RAG 接口获取相似人才、职位或简历上下文。内部接口会使用 `X-Internal-Token` 做简单保护。

## 三、AI 评估链路

### 11. 你的 AI 评估完整流程是什么？

可以这样回答：

完整流程是：用户上传简历后，系统先通过 OCR 或文本解析提取简历内容；然后根据 JD 和简历文本生成评估输入；如果配置了 Embedding 和 RAG，会先把简历文本向量化，并从向量库中检索相似人才、职位或历史简历作为上下文；最后调用 Coze 工作流输出结构化评估结果，包括候选人信息、匹配分数、优势、不足、风险点和录用建议。

### 12. OCR 在你的项目里有什么作用？

可以这样回答：

OCR 是 AI 评估链路的第一步，负责把 PDF、图片、Word 等格式的简历转换成文本。后续的 Embedding、RAG 和 Coze 评估都需要基于文本内容进行。如果没有 OCR，扫描版 PDF 或图片简历就无法进入后续智能评估流程。

### 13. 你的 OCR 支持哪些文件？

可以这样回答：

项目支持 PDF、图片和 Word 简历。PDF 会优先尝试文本提取，如果是扫描版 PDF，会走 Tesseract OCR；图片也会用 Tesseract 识别；Word 文件会通过对应解析逻辑提取文本。这样可以适配真实招聘场景中不同格式的简历。

### 14. 什么是 Embedding？为什么要用 Embedding？

可以这样回答：

Embedding 是把文本转换成语义向量。使用 Embedding 后，系统可以比较两个文本的语义相似度，而不是只看关键词是否完全一致。比如 “Golang” 和 “Go”、 “微服务” 和 “分布式后端” 在语义上相关，Embedding 能更好地表达这种相似性。

### 15. 你的 Embedding 用在哪里？

可以这样回答：

主要用在推荐服务和 RAG 检索中。系统会把人才画像、职位描述和简历文本转换成向量，存入向量索引表。查询时再把用户输入、JD 或简历文本转换成向量，通过余弦相似度查找语义相近的记录。

### 16. 什么是 RAG？你的项目中如何实现 RAG？

可以这样回答：

RAG 是 Retrieval-Augmented Generation，也就是检索增强生成。我的项目中，RAG 不是直接让大模型凭空判断，而是先从向量库中检索相似的人才、职位或历史简历，把这些检索结果作为上下文，再参与后续评估或推荐。这样可以提升评估的参考依据，也方便前端展示“为什么这样推荐”。

### 17. RAG 和普通大模型调用有什么区别？

可以这样回答：

普通大模型调用只依赖当前 prompt 和模型已有知识；RAG 会先检索项目数据库中的相关业务数据，再把检索结果加入 prompt 或评估上下文中。这样模型回答更贴近当前系统里的真实人才和职位数据，也更容易解释。

### 18. Coze 在项目里负责什么？

可以这样回答：

Coze 负责大模型工作流部分，比如结构化解析简历、根据 JD 进行匹配评分、输出优势、不足、风险点、面试问题和录用建议。我的后端负责准备输入、调用工作流、解析结果并保存到数据库，Coze 负责模型推理和复杂文本分析。

### 19. 如果 Coze 或 Embedding API 没配置，你的系统还能运行吗？

可以这样回答：

可以运行基础业务。Embedding 没配置时，系统可以使用 mock embedding，保证本地演示和推荐流程不完全中断。Coze 没配置时，核心 AI 评估会返回明确错误，部分 AI 解析功能可以降级到本地规则解析。这样可以保证系统在外部 AI 服务不可用时仍具备一定可演示性。

### 20. 你的 AI 评估结果如何保存？

可以这样回答：

评估结果保存在 `evaluation_results` 表中，包括简历 ID、人才 ID、职位 ID、解析出的候选人信息、匹配分数、匹配等级、优势、不足、风险项、原始模型输出等。同时还会保存 AI 处理过程日志，记录 OCR、Embedding、RAG、LLM 各步骤是否执行、是否成功和失败原因，方便前端展示可解释流程。

## 四、推荐算法和人岗匹配

### 21. 你的人岗匹配是怎么做的？

可以这样回答：

项目中人岗匹配分为两类：一类是规则匹配，比如技能、经验、学历、地点、薪资等维度；另一类是语义匹配，通过 Embedding 计算人才画像和职位描述的语义相似度。最终推荐结果会结合分数和推荐理由，让 HR 不只看到分数，还能看到为什么匹配。

### 22. 为什么既要规则匹配，又要语义匹配？

可以这样回答：

规则匹配比较透明，适合解释明确条件，比如学历、经验、城市、薪资范围；语义匹配适合处理文本语义，比如技能描述、项目经历和岗位职责。两者结合可以兼顾可解释性和智能化。

### 23. 余弦相似度是什么？你怎么用？

可以这样回答：

余弦相似度用于衡量两个向量方向是否接近。在我的项目中，简历、职位和人才画像会被转换成 Embedding 向量，然后用余弦相似度计算语义接近程度。分数越高，说明两个文本语义越相似。

### 24. 你的向量数据存在哪里？

可以这样回答：

当前向量数据存储在 PostgreSQL 的 JSONB 字段中，检索时在 Go 代码里计算相似度。这样做的好处是部署简单，不需要额外安装向量数据库，适合毕业设计演示规模。后续数据量变大时，可以迁移到 pgvector、Milvus 或 Elasticsearch 向量检索。

## 五、数据库设计

### 25. 项目主要有哪些数据表？

可以这样回答：

主要有用户表、人才表、职位表、简历表、投递表、评估结果表、AI 过程日志表、消息表、会话表、面试表、操作日志索引等。它们分别对应用户权限、招聘业务、AI 评估、消息通知和审计追踪。

### 26. 简历表和评估结果表为什么要分开？

可以这样回答：

简历表主要保存文件本身和基础解析信息，比如文件名、路径、大小、OCR 文本和状态；评估结果表保存 AI 评估后的业务结果，比如匹配分数、匹配等级、优势、不足和风险项。分开后，一份简历可以支持多次评估，也方便保留历史结果。

### 27. 为什么评估结果里既保存结构化字段，又保存原始 JSON？

可以这样回答：

结构化字段方便页面筛选、排序和统计，比如按匹配分数排序；原始 JSON 可以保留模型完整输出，方便后续审计、报告展示和模型效果对比。这样既满足业务查询，也保留了 AI 输出的完整性。

### 28. 你的数据库有没有做软删除？

可以这样回答：

部分模型使用 GORM 的 `DeletedAt` 字段实现软删除。这样删除后数据不会立即物理消失，方便恢复、审计和避免误删影响历史记录。

## 六、认证、权限和安全

### 29. 登录认证怎么做的？

可以这样回答：

用户登录成功后，后端生成 JWT token，token 中包含用户 ID、用户名和角色。前端把 token 保存到 localStorage，请求拦截器会自动加上 `Authorization: Bearer token`。后端服务通过 JWT 中间件解析 token，验证通过后把用户信息写入请求上下文。

### 30. RBAC 是怎么实现的？

可以这样回答：

RBAC 是基于角色的访问控制。系统中有 admin、hr_manager、recruiter、candidate 等角色。后端使用 `RoleAuth` 中间件判断当前用户角色是否允许访问某个接口。比如人才管理、职位管理、推荐管理等接口只允许管理员或 HR 角色访问。

### 31. 前端权限和后端权限有什么区别？

可以这样回答：

前端权限主要用于控制菜单和按钮显示，提升用户体验；真正的安全边界在后端。即使用户绕过前端直接请求接口，后端 JWT 和 RBAC 中间件也会校验角色权限。

### 32. 你如何保护内部接口？

可以这样回答：

普通用户请求通过 JWT 鉴权；服务间调用则使用内部接口和 `X-Internal-Token` 做区分。例如 `resume-service` 调用 `recommendation-service` 的内部 RAG 接口时，不直接暴露用户权限，而是通过内部 token 表示服务间可信调用。

### 33. 密码是怎么保存的？

可以这样回答：

用户密码使用 bcrypt 哈希后保存，数据库不保存明文密码。登录时用 bcrypt 校验输入密码和数据库中的哈希值。为了兼容历史测试数据，代码里也保留了对旧明文密码的兼容逻辑，但正式环境应统一使用哈希密码。

## 七、前端实现

### 34. 前端用了哪些技术？

可以这样回答：

前端使用 Vue3、TypeScript、Vite、Pinia、Vue Router 和 Element Plus。Vue3 负责组件化开发，Pinia 管理登录态和权限状态，Vue Router 负责后台和求职端路由，Axios 封装统一请求，Element Plus 提供 UI 组件。

### 35. 前端怎么区分后台管理端和求职者门户？

可以这样回答：

路由上分成两条线：后台管理端主要在 `/login` 和 `/dashboard` 等路径下，求职者门户在 `/portal` 下。路由守卫会根据登录状态和用户角色做跳转，比如 candidate 角色不能进入后台管理页面。

### 36. 前端请求是怎么统一处理的？

可以这样回答：

项目封装了 Axios 请求实例，统一设置 `baseURL`、超时时间、请求拦截器和响应拦截器。请求拦截器负责自动添加 JWT token；响应拦截器统一处理 401、403、404、500 等错误，并在 token 过期时引导用户重新登录。

### 37. WebSocket 前端怎么实现？

可以这样回答：

前端封装了 `WebSocketService`，统一连接 Gateway 暴露的 `/api/v1/ws`。它支持连接状态维护、自动重连、按消息类型订阅处理器和默认通知提示。聊天页面通过组合式函数订阅消息，组件卸载时自动取消订阅。

## 八、消息、面试和日志

### 38. 消息系统怎么设计？

可以这样回答：

消息系统分为站内信和实时聊天。站内信用于系统通知、面试提醒、投递状态变化等；实时聊天使用 WebSocket，由 Hub 管理在线连接、会话订阅和消息推送。离线消息会保存到数据库，用户下次打开会话仍然可以看到。

### 39. 面试安排后如何通知候选人？

可以这样回答：

面试服务创建面试记录后，会异步调用消息服务或写入消息表，生成面试通知。候选人可以在消息中心看到面试时间、方式、地点、面试官等信息。

### 40. 操作日志有什么作用？

可以这样回答：

操作日志用于审计和问题排查。中间件会记录请求用户、路径、方法、状态码、耗时、操作类型和模块等信息，并写入 Elasticsearch。后台操作日志页面可以按服务、用户、路径、操作类型和时间范围查询。

## 九、Swagger、启动和部署

### 41. 你的 Swagger 文档在哪里？

可以这样回答：

Swagger 文档在 `backend/gateway/docs` 目录下，网关服务启动后可以通过 Gateway 暴露的 Swagger UI 查看接口文档。项目使用的是 Go 的 swaggo 相关工具，通过注释生成 OpenAPI 文档。

### 42. 项目怎么启动？

可以这样回答：

本地开发可以运行项目根目录下的 `./start-all.sh`，它会启动各个后端微服务、API Gateway 和前端。停止时运行 `./stop-all.sh`。启动脚本里做了端口清理、PID 管理和服务健康检查，避免重复启动导致端口冲突和电脑卡顿。

### 43. 项目有哪些端口？

可以这样回答：

前端默认是 `5173`，API Gateway 是 `8080`。各个微服务有自己的端口，例如用户服务、职位服务、简历服务、消息服务、推荐服务等。前端主要通过 Gateway 访问后端，不直接访问每个微服务端口。

## 十、测试和性能

### 44. 你做了哪些测试？

可以这样回答：

项目包含接口测试、核心业务流程测试和性能测试。测试内容覆盖登录、用户、职位、人才、简历上传、投递、AI 评估、推荐、消息、面试等接口。项目文档中也整理了测试报告和验收报告。

### 45. 性能方面你做了哪些考虑？

可以这样回答：

职位详情和热门职位使用 Redis 做缓存和排行；日志写入采用异步方式，避免影响业务接口响应；AI 评估这类耗时操作设置了较长超时时间，并通过状态字段和过程记录展示执行进度。启动脚本也避免重复进程占用资源。

### 46. AI 评估为什么会比较慢？

可以这样回答：

AI 评估涉及文件读取、OCR、Embedding、RAG 检索和 Coze 工作流调用，其中 OCR 和外部大模型调用都比较耗时。因此项目把 AI 评估和普通 CRUD 区分处理，接口超时时间也设置得更长。

## 十一、老师可能追问的细节

### 47. 你项目中 `resume-service` 和 `evaluator-service` 有什么区别？

可以这样回答：

毕业设计主链路使用的是 `resume-service` 中的 AI 评估功能，它和前端后台页面、简历管理、评估结果页面直接关联。`evaluator-service` 更像一个独立评估后台，偏外部招聘系统抓取、批量评估、钉钉推送和报告导出，不是当前毕业设计主 AI 入口。

### 48. 为什么不把所有 AI 逻辑都放在一个服务里？

可以这样回答：

因为 AI 链路里有不同职责。`resume-service` 负责简历文件、评估结果和业务状态；`recommendation-service` 负责 Embedding、向量索引、RAG 检索和推荐算法。这样拆分后职责更清晰，也方便后续单独优化推荐能力。

### 49. 如果数据量很大，你现在的 RAG 方案有什么问题？

可以这样回答：

当前向量存在 PostgreSQL JSONB 中，并在 Go 里计算相似度，适合毕业设计演示和中小规模数据。如果数据量很大，检索性能会下降。后续可以迁移到 pgvector、Milvus 或 Elasticsearch 向量检索，并增加索引和分页检索策略。

### 50. 你觉得项目最大的难点是什么？

可以这样回答：

最大难点是把 AI 能力和真实业务流程结合起来，而不是只做一个单独的大模型调用。比如简历上传后要经过 OCR、Embedding、RAG、Coze 评估、结果落库、前端展示和过程解释，每一步都要考虑失败降级和数据一致性。

## 十二、项目不足与改进

### 51. 你的项目还有哪些不足？

可以这样回答：

第一，向量检索目前用 PostgreSQL JSONB 和 Go 计算，相比专业向量数据库性能有限。  
第二，AI 评估依赖外部 Coze 和 Embedding API，稳定性会受网络和 API Key 影响。  
第三，部分微服务仍共享同一个数据库，严格意义上的微服务数据隔离还可以继续优化。  
第四，权限系统目前以后端角色校验为主，细粒度按钮权限和动态权限管理还可以完善。

### 52. 后续你会怎么优化？

可以这样回答：

后续可以从四个方向优化：一是引入 pgvector 或 Milvus 提升向量检索性能；二是加入消息队列，把批量 AI 评估改成异步任务；三是完善模型评估反馈机制，让 HR 可以对 AI 结果做人工反馈；四是加强自动化测试、监控告警和容器化部署。

### 53. 如果老师问“这个项目有什么创新点”，怎么答？

可以这样回答：

创新点主要有三个。第一，把 OCR、Embedding、RAG 和 Coze 大模型组合成完整的简历智能评估链路。第二，不只输出分数，还保存评估过程和证据，让 AI 结果可解释。第三，把 AI 能力嵌入招聘业务闭环中，从简历上传、职位匹配、推荐、面试到消息通知都有联动。

### 54. 如果老师问“这个项目和普通管理系统有什么区别”，怎么答？

可以这样回答：

普通管理系统主要是增删改查，而我的项目在基础招聘管理之外，增加了智能简历解析、语义匹配、RAG 检索增强、AI 评估报告和过程可解释展示。也就是说，系统不仅管理数据，还能辅助 HR 做筛选和决策。

## 十四、必须背熟的 5 个核心回答

### 1. 项目核心

本项目是一个智能人才运营平台，核心是把 OCR、Embedding、RAG 和 Coze 大模型工作流接入招聘流程，实现简历解析、人岗匹配、智能推荐和可解释 AI 评估。

### 2. AI 流程

AI 评估流程是：简历上传 -> OCR/文本提取 -> Embedding 向量化 -> RAG 检索相似上下文 -> Coze 工作流评分 -> 评估结果和过程日志落库 -> 前端展示。

### 3. RAG 作用

RAG 的作用是先从系统已有的人才、职位和简历数据中检索相似内容，再辅助 AI 生成评估或推荐结果，让结果更贴近业务数据，也更容易解释。

### 4. 微服务设计

系统按用户、职位、人才、简历、推荐、消息、面试、日志等业务边界拆分服务，通过 API Gateway 统一入口，前端不需要关心后端具体服务端口。

### 5. 项目不足

当前项目适合毕业设计演示规模，后续可以引入专业向量数据库、异步任务队列、动态权限管理、监控告警和更完善的测试体系，让系统更接近生产环境。
